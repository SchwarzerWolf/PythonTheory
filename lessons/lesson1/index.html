    На что обращать внимание при первом рефакторинге

    Ниже — чек-лист вещей, на которые стоит смотреть при первом проходе по чужому (или своему старому) коду. Большая часть пунктов основана на PEP 8 и общепринятых практиках чистого кода, адаптированных под примеры из нашего домена — молекулы и SMILES.

    Имена переменных

    Имя должно объяснять, что лежит в переменной, без необходимости читать код вокруг.

    # Плохо: неясно, что это за строка и что значит флаг
s = "CN1C=NC2=C1C(=O)N(C(=O)N2C)C"
m = Chem.MolFromSmiles(s)
f = m is not None

# Хорошо: имена сами объясняют смысл
smiles = "CN1C=NC2=C1C(=O)N(C(=O)N2C)C"
molecule = Chem.MolFromSmiles(smiles)
is_valid_smiles = molecule is not None
    Рекомендации: - Лучше избегать однобуквенных имён (s, m, x), кроме счётчиков в коротких циклах (i, j) или устоявшихся обозначений (df) - Имя булевой переменной должно звучать как вопрос: is_valid_smiles, has_ring, can_dock - Лучше не экономить буквы mw → molecular_weight, cmpd → compound - Лучше не зашивать тип данных в название — molecules_list несёт такую же смысловую нагрузку, как и просто molecules, но при изменении типа добавляет либо неконсистентность, либо кучу изменений - Не использовать зарезервированные имена (id, list, etc)

    Константы

    «Магические числа» и строки лучше выносить в константы с понятным именем — это добавляет пояснений к коду и ускоряет понимание того, куда должны вноситься изменения

    # Плохо: в середине кода 0.5 непонято за что отвечает
for molecule in molecules:
    if calculate_similarity(molecule, etalon) < 0.5:
        print("Молекулы не похожи")

# Хорошо - знаем за что отвечает параметр и видим где его менять
SIMILARITY_THRESHOLD = 0.5

for molecule in molecules:
    if calculate_similarity(molecule, etalon) < SIMILARITY_THRESHOLD:
        print("Молекулы не похожи")

    Рекомендации: - Константы пишутся UPPER_SNAKE_CASE и объявляются в начале модуля (или в отдельном constants.py) - Если число используется один раз и его смысл очевиден из контекста (range(1) для единственной итерации) — выносить в константу не обязательно

    Отступы

    # Плохо: смешаны отступы в 2 и 4 пробела, лишняя вложенность
if mol is not None:
   if molecular_weight > 500:
     print("heavy")
   else:
     print("druglike")

# Хорошо: единый отступ 4 пробела
MAX_DRUGLIKE_MOLECULAR_WEIGHT = 500
if mol is not None:
    if molecular_weight > MAX_DRUGLIKE_MOLECULAR_WEIGHT:
        print("heavy")
    else:
        print("druglike")

    Рекомендации: - Настроить редактор на 4 пробела и запрет табов (PEP 8) — опечатки отступов часто незаметны глазом

    Длина строк

    # Плохо: строка не влезает в экран, приходится скроллить по горизонтали
is_druglike = molecular_weight <= MAX_DRUGLIKE_MOLECULAR_WEIGHT and calculate_similarity(molecule, etalon) >= SIMILARITY_THRESHOLD

# Хорошо: строка разбита по логическим скобкам, видно оба условия сразу
is_druglike = (
    molecular_weight <= MAX_DRUGLIKE_MOLECULAR_WEIGHT
    and calculate_similarity(molecule, etalon) >= SIMILARITY_THRESHOLD
)

    Рекомендации: - Ограничивай строки 79–99 символами (PEP 8 рекомендует 79, многие проекты договариваются на 88–99) — настрой линтер (ruff/flake8), чтобы он сам подсвечивал превышение - Разбивай длинные выражения по скобкам ()/[]/{} — Python сам продолжает строку внутри них, без \ на конце строки - Длинная строка — частый симптом того, что переменная или функция делает слишком много сразу; иногда разбиение на отдельные переменные с понятными именами лучше, чем просто перенос строки

    Пробелы и trailing commas

    # Плохо: пробелы расставлены случайно, нет висячей запятой в многострочном списке
smiles_db = {
    "Caffeine":"CN1C=NC2=C1C(=O)N(C(=O)N2C)C",
    "Aspirin" : "CC(=O)OC1=CC=CC=C1C(=O)O"
}
calculate_similarity( molecule , etalon )
x=1
y = [1,2,3]

# Хорошо: один пробел вокруг операторов, пробел после запятой, висячая запятая
smiles_db = {
    "Caffeine": "CN1C=NC2=C1C(=O)N(C(=O)N2C)C",
    "Aspirin": "CC(=O)OC1=CC=CC=C1C(=O)O",
}
calculate_similarity(molecule, etalon)
x = 1
y = [1, 2, 3]

    Рекомендации: - Один пробел вокруг =, ==, + и других операторов; без пробела сразу после ( или перед ) - Пробел после запятой, но не перед ней: (a, b, c), а не (a,b , c) - Висячая запятая (trailing comma) после последнего элемента в многострочных списках, словарях и вызовах функций — следующая правка добавит строку, а не изменит существующую (в git diff видно только новую строку, а не +1 строку с лишней запятой на старой) - В однострочных конструкциях висячую запятую не ставят: [1, 2, 3], а не [1, 2, 3,]

    Расположение элементов

    Порядок, в котором читатель встречает код, должен соответствовать логике, а не истории правок

    # Плохо: импорты раскиданы по файлу, константа объявлена в середине,
# переменная используется раньше, чем стало понятно, что это за данные
caffeine_smiles = "CN1C=NC2=C1C(=O)N(C(=O)N2C)C"
print(Descriptors.MolWt(Chem.MolFromSmiles(caffeine_smiles)))

from rdkit import Chem
from rdkit.Chem import Descriptors

MAX_DRUGLIKE_MOLECULAR_WEIGHT = 500

# Хорошо: сначала импорты, потом константы, потом основной код
from rdkit import Chem
from rdkit.Chem import Descriptors

MAX_DRUGLIKE_MOLECULAR_WEIGHT = 500

caffeine_smiles = "CN1C=NC2=C1C(=O)N(C(=O)N2C)C"
print(Descriptors.MolWt(Chem.MolFromSmiles(caffeine_smiles)))

    Рекомендации: - Внутри файла: импорты → константы → основной код - Данные, которые логически относятся друг к другу (например, все константы правила Липинского), стоит объявлять рядом, а не раскидывать по файлу - Одновременно с этим блоки данных лучше отделять пустой строкой

    Импорты

    # Плохо: всё в одну кучу, есть wildcard-импорт и неиспользуемый импорт
from os import *
import json, sys
from rdkit import Chem
from .smiles_utils import canonicalize_smiles, calculate_similarity, molecular_formula, sanitize_molecule  # molecular_formula не используется

# Хорошо: сгруппировано (стандартная библиотека / сторонние / локальные),
# явные импорты, алфавитный порядок внутри группы
import json
import sys

from rdkit import Chem

from .smiles_utils import (
    calculate_similarity, 
    canonicalize_smiles,
    sanitize_molecule,
)

    Рекомендации: - Три группы импортов, разделённые пустой строкой: стандартная библиотека → сторонние пакеты → локальные модули - Никаких from module import * — непонятно, откуда взялось имя в коде - Удалять неиспользуемые импорты (линтеры ruff/flake8 может найти их автоматически) - Если импортов больше 3, лучше переносить их по строчкам

    Unused values

    # Плохо: переменная создана и не используется, результат вызова проигнорирован
canonical = Chem.MolToSmiles(molecule)
molecular_weight = Descriptors.MolWt(molecule) # не используется ниже
save_to_database(canonical)  # результат (успех/ошибка) нигде не проверяется

# Хорошо: убрали лишнее, явно обработали результат
canonical = Chem.MolToSmiles(molecule)
was_saved = save_to_database(canonical)
if not was_saved:
    logger.warning("Failed to save molecule %s", Chem.MolToSmiles(mol))

    Рекомендации: - Неиспользуемые переменные и параметры — сигнал, что код менялся по частям и не был доведён до конца - Если переменная нужна только для читаемости промежуточного шага — это нормально, но тогда она должна использоваться дальше

    Комментарии

    Комментарий должен объяснять почему, а не что — само «что» видно из кода, если он написан понятно.

    # Плохо: комментарий дублирует код и не несёт новой информации
# увеличиваем счётчик атомов на 1
atom_count += 1

# Плохо: закомментированный мёртвый код вместо удаления
# mol = Chem.MolFromSmiles(smiles, sanitize=False)
# return mol

# Хорошо: комментарий объясняет неочевидную причину решения
# Санитизируем отдельно: по умолчанию RDKit бросает исключение на валентность,
# а нам для этого пайплайна нужно получить None и обработать его самим
mol = Chem.MolFromSmiles(smiles, sanitize=False)
Chem.SanitizeMol(mol, catchErrors=True)

    Рекомендации: - Удалять закомментированный код — для истории есть git - Проверять, что комментарий не разошёлся с кодом после правок (устаревший комментарий хуже отсутствующего)

    Обработка ошибок

    # Плохо: ловим всё подряд и молча глушим ошибку
try:
    smiles = smiles_db[name]
except Exception:
    pass

# Хорошо: ловим конкретное исключение и явно решаем, что делать дальше
try:
    smiles = smiles_db[name]
except KeyError:
    logger.info("No SMILES found for %s", name)
    smiles = None

    Рекомендации: - Никогда не использовать except Exception: pass - Осторожно использовать except: или except Exception as e - Ловить самое конкретное исключение, какое возможно

    Консистентность

    # Плохо: одни и те же данные оформлены по-разному в разных местах
caffeine = {"Smiles": "CN1C=NC2=C1C(=O)N(C(=O)N2C)C", "mw": 194.19}
aspirin = {'smiles': "CC(=O)OC1=CC=CC=C1C(=O)O", "molecular_weight": 180.16}

# Хорошо: единый набор ключей, единый стиль именования и кавычек
caffeine = {"smiles": "CN1C=NC2=C1C(=O)N(C(=O)N2C)C", "molecular_weight": 194.19}
aspirin = {"smiles": "CC(=O)OC1=CC=CC=C1C(=O)O", "molecular_weight": 180.16}

    # Плохо: number & count как будто несут разную смысловую нагрузку 
atoms_number = 2
molecules_count = 1

# Хорошо: единый нейминг
atoms_count = 2
molecules_count = 1

    Рекомендации: - Один стиль именования на весь проект (в Python — snake_case для переменных и ключей) - Один стиль кавычек (например, всегда ") - Одинаковый набор полей для однотипных данных — если у одной молекулы есть molecular_weight, он должен называться и считаться одинаково у всех остальных - Одинаковые названия для одинаковых концепций

    Docstrings

    Докстринг — это первое, что видит человек (или IDE), заглянувший в модуль. Он должен объяснять контракт: что за данные, в каком формате, какие есть ограничения — то, что не всегда видно по одним именам переменных.

    # Плохо: непонятно, что за формат SMILES ожидается в этом модуле
"""Утилиты для работы с молекулами."""

MAX_DRUGLIKE_MOLECULAR_WEIGHT = 500

# Хорошо: докстринг объясняет формат данных и неочевидные ограничения
"""Утилиты для работы с молекулами.

Все SMILES здесь ожидаются каноническими (RDKit, без явных атомов водорода).
"""

MAX_DRUGLIKE_MOLECULAR_WEIGHT = 500

    Рекомендации: - Докстринг пишется в тройных кавычках в самом начале модуля — до импортов и констант - Первая строка — краткое описание одним предложением, без пересказа кода - Указывай в докстринге то, что не выражается типами: формат данных, единицы измерения, допущения («smiles без стереохимии», «molecular_weight в г/моль»)

    Работа с файловой системой

    # Плохо: путь собран конкатенацией строк, файл не закрывается явно
path = "data/" + "molecules" + ".sdf"
f = open(path)
content = f.read()

# Хорошо: os.path.join собирает путь, контекстный менеджер сам закрывает файл
import os

path = os.path.join("data", "molecules.sdf")
with open(path) as f:
    content = f.read()

    Рекомендации: - Собирай пути через os.path.join, а не конкатенацией строк — одинаково работает на Windows и Linux (\ против /). Исключение: работа с AWS S3 - Открывай файлы через with ... as — менеджер контекста закроет файл, даже если внутри блока вылетит исключение - Не зашивай в код абсолютные пути вроде C:/Users/kristina/data — используй относительные пути от корня проекта

    # Плохо: при повторном запуске скрипта упадёт с FileExistsError
output_dir = os.path.join("data", "results")
os.mkdir(output_dir)

# Хорошо: exist_ok делает создание папки идемпотентным —
# скрипт можно запускать повторно, ошибки не будет, даже если папка уже есть
output_dir = os.path.join("data", "results")
os.makedirs(output_dir, exist_ok=True)

    Рекомендации: - os.makedirs(path, exist_ok=True) создаёт все промежуточные папки и не падает, если они уже существуют — без exist_ok повторный запуск скрипта кидает FileExistsError - os.mkdir создаёт только последнюю папку, требует, чтобы родительские уже существовали, и не принимает exist_ok — для путей с несколькими уровнями и идемпотентности нужен os.makedirs
